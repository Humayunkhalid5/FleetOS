## Product and design goals

FleetOS is a multi-company service and operations platform. Its interface serves three audiences:

- **Customers** discover providers, request and track work, communicate with companies, and review payments and service outcomes.
- **Companies** run a tenant-specific workspace for requests, services, staff, inventory, customers, messages, reviews, and analytics.
- **Super Admins** use a separate console to verify companies and oversee platform operations.

The product is designed as one connected workflow rather than three unrelated dashboards: customer bookings move through company dispatch and completion, with administrative oversight and persisted history along the way. Company workspaces also adapt terminology and available modules to a company's selected business category.

All three surfaces share one semantic token set, so a colour or theme change lands everywhere at once. Each surface keeps its own density:

- The **public/customer experience** uses open space, large type and a glass top navigation, with a bottom tab bar on phones.
- The **company workspace** uses a compact, grouped sidebar, a sticky header with search, Copilot, notifications and theme toggle, and information-dense tables.
- The **Super Admin console** uses a fixed sidebar, metrics, searchable/paginated tables and explicit approval and status treatments.

## How the project is assembled

### Runtime surfaces

| Surface | Source | Local address | Main role |
|---|---|---|---|
| Client and company portal | `client/` | `http://localhost:5173` | Public pages, customer flows, and company workspace |
| Super Admin console | `admin/` | `http://localhost:5174` | Platform-wide administration |
| API and realtime service | `server/` | `http://localhost:5000` | REST API, authentication, persistence, and Socket.IO |

The client and company portal share one React application, with role gates and route-specific layouts. The Admin console is a separate React/Vite application. Both call the Express API; MongoDB is the persistent source of truth. Socket.IO carries live updates for supported workflows such as chat and booking progress.

### Technology

- **Frontend:** React 19, Vite, React Router, Tailwind CSS, and custom CSS.
- **Motion and graphics:** CSS keyframes only (no animation library); Three.js for the interactive 3D city in the home-page hero; Leaflet for map surfaces.
- **Fonts and icons:** self-hosted Inter Variable and JetBrains Mono (`@fontsource`), and a subset Material Symbols font generated by `npm run icons`. Nothing is loaded from Google Fonts.
- **Backend:** Node.js, Express, Mongoose, MongoDB, and Socket.IO.
- **Identity:** Server-issued JWT sessions and role-based route/API access.
- **Startup and build:** Root `npm run dev` coordinates the API, client, and Admin apps. Root `npm run build` builds both frontend applications. Root `npm test` runs the server's Node test suite.

The root development coordinator starts the API first and waits for its health endpoint before launching both browser applications. The server connects to MongoDB and seeds missing development records; production requires an explicitly configured database and does not load demonstration records.

### Request and data flow

1. The browser renders the route and checks the authenticated user's role where necessary.
2. A page calls the shared client API service or the Admin app's API helper.
3. Express applies CORS, request IDs, common security headers, rate limits, JSON parsing, and route handlers.
4. Controllers validate the operation and use Mongoose models for MongoDB reads and writes.
5. Relevant events may be broadcast to authorized Socket.IO clients.
6. The shared live-data layer (`useLiveQuery`) revalidates every screen that depends on the changed data, so no page needs a manual reload.

Company-facing server operations are scoped from the authenticated company identity; the UI's company identifier or display state is not the data security boundary.

## Product surfaces and navigation

### Public and customer portal

Public routes include the homepage, sign-in, customer registration, company registration, About, and Contact. Customer routes cover:

- Company marketplace and company details
- Booking customization and confirmation
- Booking history, live tracking, and service review
- Customer profile, chat, payments, reviews, and notifications

The homepage introduces the service marketplace and booking process. Company discovery and details lead into a booking flow; the customer can then follow the job and review the outcome.

### Company workspace

The company portal is a role-protected workspace with a persistent side navigation and top-level page header. Its modules include:

- Overview/dashboard
- Requests/bookings and Smart Dispatch
- Staff/technicians
- Inventory
- Services or category-specific offerings
- Customers, messages, and reviews
- Analytics, company profile, and settings

The navigation labels are intentionally configurable. For example, a retail company may see **Orders**, **Store staff**, and **Products & offers**, while a service company sees **Requests**, **Technicians**, and **Services**. The server's business-category workspace configuration determines module visibility and terminology; this is product behavior, not just decorative copy.

### Super Admin console

The separate Admin application contains:

- Platform overview and metrics
- Company registration requests, company registry, and company access controls
- Reviews and users
- Jobs/bookings, payments, and support
- System health (database, API round trip, live channel, server uptime/memory), Reports (platform KPIs, monthly revenue with month-over-month change, job status shares, and one-click CSV exports of every record set), and security settings

Its fixed desktop sidebar and sticky top bar frame the current section; the top bar shows a one-line description of each section. Tables and status labels support operational scanning; company documents open in a dedicated viewer before an approval decision.

### Core service workflow reflected in the UI

The primary booking lifecycle is:

`Pending → Assigned → En Route → Arrived → In Progress → Completed → Paid`

The status is used across customer tracking, company dispatch/booking pages, payment confirmation, and Admin oversight. Status labels must remain text-readable and should not rely on color alone.

## Visual design system

FleetOS uses **one semantic token contract** for the client, company and Admin apps. Tokens are RGB triplets in `client/src/styles/tokens.css`, defined for `:root` (light) and `[data-theme='dark']`. Tailwind maps them to utility names (`bg-surface`, `text-muted`, `border-line`, `bg-brand-soft`, `text-success-fg` …) through `rgb(var(--token) / <alpha-value>)`, so opacity modifiers work. The Admin stylesheet imports the same file.

### Core tokens

| Token | Light | Dark | Use |
|---|---|---|---|
| `canvas` | `#F4F7FA` | `#060B15` | Page background (dark adds soft radial "aurora" glows) |
| `surface` | `#FFFFFF` | `#0C1423` | Cards, panels, tables |
| `raised` | `#FFFFFF` | `#111B2E` | Menus, modals, popovers |
| `sunken` | `#EEF2F6` | `#090F1B` | Inputs, tab rails, inset areas |
| `ink` / `muted` / `subtle` | navy → slate | near-white → steel | Primary, secondary and tertiary text |
| `line` / `line-strong` | low-contrast slate | low-contrast steel | Borders and dividers |
| `brand` | `#2563EB` | `#3E74E8` | Primary actions, active navigation |
| `accent` | cyan | cyan | Live/progress highlights |

Each semantic state — `success`, `warning`, `danger`, `info`, `violet` — has a base colour plus `-soft` (tinted background), `-fg` (readable text on that background) and `-line` (border) variants, tuned separately for each theme so contrast holds in both.

### Status semantics

`StatusBadge` (client) and `Status` (Admin) always render **icon + text**, never colour alone:

- **Warning:** Pending, Open, Unpaid, Low stock
- **Info:** Assigned, En Route, Arrived, On Job
- **Brand:** In Progress
- **Success:** Completed, Paid, Recorded, Approved, Active, Available
- **Danger:** Cancelled, Rejected, Suspended, Out of stock
- **Neutral:** Off Duty, Draft, Inactive

`LifecycleRail` shows the seven-step booking lifecycle; in narrow containers it switches (via a container query) from step labels to a "Step n of 7 · Current → Next" caption.

### Typography

- **Inter Variable** for everything; **JetBrains Mono** only for references and identifiers (booking numbers, SKUs).
- Page titles are semibold and tight-tracked; body copy is 13.5–15px; numbers use `tabular-nums`.
- **Material Symbols Outlined** is the icon font. Only the icons used in source are kept (`scripts/subset-icons.py`, ~265 KB instead of ~4 MB). Run `npm run icons` after adding a new icon name.

### Shape, elevation and surfaces

- Radius scale: 8px (small controls) → 12px (inputs, buttons) → 16px (cards) → 24px (modals).
- Shadows are tokenised (`shadow-xs`, `shadow-card`, `shadow-pop`) and become deeper/darker in dark mode.
- `.glass` is used for sticky headers (90% surface opacity with blur).
- Named component classes in `client/src/index.css`: `.card`, `.btn` (+ `-primary`, `-secondary`, `-soft`, `-ghost`, `-success`, `-danger`, `-danger-solid`, sizes), `.input`/`.select`/`.textarea`, `.chip`, `.badge-*`, `.table`, `.nav-pill`, `.skeleton`.

### Dark theme

The dark theme is a designed palette, not an inversion: deep blue-black canvas, layered blue-grey surfaces, brighter brand blue and cyan accent, tuned `-soft/-fg` state pairs, and a filtered dark map style. The theme follows the operating-system preference until the user picks one; the choice is stored per app (`fleetos-theme`, `fleetos-admin-theme`). An inline script in `index.html` applies the theme before first paint, so there is no light flash.

### Imagery, maps and motion

- The FleetOS mark (`components/ui/Logo.jsx`, `public/favicon.svg`) appears in every shell and in the loader.
- Company covers are generated, text-free SVGs; companies can upload their own logo and cover.
- `HeroScene` renders a small interactive 3D city in the home hero (vans drive to job pins; drag to turn it). It loads lazily, pauses when off-screen or in a background tab, follows the active theme, and renders one still frame under `prefers-reduced-motion`.
- Leaflet powers live tracking; tiles are dimmed in dark mode. Wheel zoom turns on only after the map is clicked, so page scrolling never zooms it.
- Revenue charts always show the last six calendar months (empty months as 0), with bars capped at 44px so sparse data still reads as a trend.
- Motion is limited to short CSS transitions: page rise-in, modal scale-in, the branded loader and the top progress bar. All are disabled under reduced motion.

## How to apply the design

1. **Use tokens, never hex.** Use `bg-surface`, `text-muted`, `border-line`, `bg-success-soft text-success-fg`, etc. Both themes then work automatically.
2. **Use the shared components** from `components/ui` (`StatusBadge`, `LifecycleRail`, `StatCard`, `EmptyState`, `Alert`, `Skeleton*`, `Tabs`, `Modal`, `Field`, `Avatar`, `Stars`).
3. **Use the feedback context** (`useFeedback()` from `hooks/useFeedback.js`) for confirm, prompt and toast. Never call `window.alert/confirm/prompt`.
4. **Set the page header with `usePageChrome({ title, subtitle, actions, search, backTo })`** (`hooks/usePageChrome.js`). The layout renders it. Customer pages outside the main tabs get a back button automatically; pass `backTo` for a logical parent (company → companies, booking → company, tracking → bookings) or `showBack: false` to hide it.
5. **Fetch with `useLiveQuery(key, { events })`.** Pass the socket events that should refresh the screen.
6. **Keep state explicit.** Status chips need visible text.
7. **Check mobile and both themes.** Tables either scroll inside their card or switch to a card list under `md`.

## Responsive behavior, motion, and accessibility

- **Customer portal:** top navigation on desktop; on phones, a bottom tab bar (Companies, Bookings, Messages, Payments, Reviews).
- **Company workspace:** 248px sidebar on desktop; on phones, a slide-in drawer, with header search moved under the title. The Requests table becomes a card list on phones.
- **Admin:** the sidebar stacks under 860px; metrics go from five columns to three to two; tables scroll inside their panel.
- Every route was checked at 390px and 1440px in both themes with no horizontal page scroll.
- All controls have visible focus rings. Dialogs trap focus, close on Escape, and restore focus on close.
- Decorative graphics are `aria-hidden`, and reduced-motion disables animation.

## Live data and navigation

- **No reloads.** `useLiveQuery` keeps a stale-while-revalidate cache shared across screens. It revalidates on matching Socket.IO events, after any successful API write, on reconnect, on window focus or tab visibility, and when the network comes back online.
- **Realtime.** One socket per session (`RealtimeProvider`). Events include `booking:created`, `booking:updated`, `workspace:updated`, `review:created`, chat messages and `platform:updated` for the Admin console.
- **Fast navigation.** Pages are lazy chunks with `.preload()`. Chunks for the current portal are preloaded when the browser is idle, and navigation links prefetch their data on hover or focus, so a page usually opens with its data ready.
- **Branded loading.** The persistent shell (with the FleetOS logo) stays on screen while a page loads. A thin top progress bar shows background fetches, and skeletons replace content only on a page's first load.
- **Notifications.** Companies get a toast for every new booking. Customers get a toast for every status change, except while they are already watching that job.

## Status of earlier design issues

| Earlier issue | Status |
|---|---|
| Three visual systems drifting | **Resolved.** One token file shared by client, company and Admin. |
| Broad `!important` utility remaps | **Resolved.** The old 3,800-line override sheet was replaced by base styles plus named components. |
| Misleading accent token names | **Resolved.** Tokens are semantic (`success`, `warning`, …) with distinct hues. |
| Unverified dark theme | **Resolved.** A designed dark palette, checked route by route in both themes. |
| Stale style sources (`App.css`, empty `main.css`) | **Resolved.** Removed. |
| Remote font loading | **Resolved.** Fonts are self-hosted and the icon font is subset. |
| Bundle weight | **Improved.** Animation libraries removed; Three.js only loads on the home page; vendor chunks split. |
| Accessibility and visual regression | **Improved.** Icon+text statuses, focus rings, dialog focus handling, and a repeatable screenshot sweep. |
| Fleet/vehicle terminology | **Resolved.** Copy describes a multi-industry service platform; workspace labels follow business category. |
